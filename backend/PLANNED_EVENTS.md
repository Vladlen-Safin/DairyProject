# Занятия без ID в выгрузке 1С

## Поведение старого приложения

В `e_diary_import.module`:

- `e_diary_import_load_events` разрешает пустой `ext_id` (`can_be_empty`).
- `e_diary_import_add` отключает поиск по ключу, если ID пустой: каждое такое
  занятие вставляется отдельно. Поле `ext_id` остаётся NULL.
- Обработка дочерних оценок, комментариев и пропусков пропускается для событий
  без внешнего ID (`e_diary_import_load_table`). Домашнее задание сохраняется
  непосредственно в событии.
- При первом events-файле нового обмена удаляются прежние события с NULL ID.
- Страницы читают занятия по группам и датам без требования внешнего ID.

Таким образом, безымянные занятия — заменяемый снимок расписания. Старое
приложение не сопоставляет плановое и проведённое занятие по предмету/дате:
предыдущее плановое удаляется при обновлении снимка, проведённое сохраняется по ID.
Это не доказывает, какое конкретное действие преподавателя в 1С создаёт ID.

## Исправление

Ранее пустые ID превращались в общий уникальный ключ `''`. Новая миграция
разрешает NULL в `ediary_events.ext_id`. События без ID сначала сохраняются в
`ediary_planned_events_stage` по MessageNo, имени файла и позиции в XML.
Повторная попытка не дублирует строки; разные файлы и порции CONTINUE дополняют
один снимок. Источник должен сохранять файлы сообщения неизменными до завершения.

После успешного завершения всех events-файлов из filelist снимок публикуется
одной транзакцией: прежние NULL/пустые ID удаляются, новые строки вставляются
по отдельности. События с заполненным ID сохраняются. При ошибке events-файла
или CONTINUE старый снимок остаётся доступен. При ошибке публикации транзакция
полностью откатывается. Во время обмена проведённые занятия уже могут обновиться,
а старый плановый снимок ещё остаётся до завершения обмена.

Служебный чекпоинт `__planned_snapshot__` со статусом `published` предотвращает
повторную публикацию того же сообщения, в том числе после сбоя отправки result.xml.
Он сохраняется в истории; это не признак незавершённого импорта. Временные строки
текущего сообщения очищаются после отправки результата и отметки завершения.

Как и в старом приложении, предполагается, что каждый обмен с events-файлами
содержит полный актуальный набор занятий без ID. Успешный обмен без таких занятий
очищает прежний плановый снимок. Обмен без events-файлов снимок не меняет.
Номера сообщений должны быть уникальны в пределах текущей истории обмена.
Одновременный обмен разными сообщениями не поддерживается существующим общим
файловым кэшем; запускайте обмен последовательно.

## Установка на сервере

Перенести обновлённый код, затем из `/var/www/DairyProject/backend`:

```bash
sudo systemctl stop ediary-backend
npm run build
sudo -u ediary npm run migrate -- 003_planned_events.sql
sudo systemctl start ediary-backend
sudo journalctl -u ediary-backend -f -n 0 -o cat
```

Выполнять команды по очереди; запускать службу только после успешной сборки
и миграции. Для миграции нужны права владельца таблицы в PostgreSQL. Использовать
тот же DATABASE_URL, что и у службы. Миграция добавляет таблицу и снимает NOT NULL,
не очищает рабочую базу. Перед применением сохранить обычную резервную копию БД.

После установки нужна новая выгрузка с новым MessageNo, содержащая плановые
занятия: уже обработанное сообщение вернёт ALREADY. В журнале должно появиться
`events.publishPlanned` со статусом OK, затем `result.upload` со статусом OK.
При успешной публикации также удаляется повреждённая строка с пустым внешним ID,
оставшаяся от прежнего импортёра, вместе с её дочерними записями по внешним ключам.
Данные, ранее объединённые в эту строку, восстанавливаются из новой выгрузки.

Проверка:

```sql
SELECT date, lesson, group_id, homework
FROM ediary_events
WHERE ext_id IS NULL AND date = DATE '2026-10-13'
ORDER BY group_id, lesson;
```

## Проверки

`plannedEvents.integration.test.mjs` использует отдельную случайную схему PostgreSQL
и удаляет её после теста. Проверяет 266 пустых ID, повторную загрузку, несколько
файлов, CONTINUE, замену планового снимка, появление проведённого события, откат при
ошибке публикации и очистку повреждённого пустого ID. Запуск из backend:

```powershell
$env:RUN_IMPORT_DB_TESTS = '1'
node --test tests/plannedEvents.integration.test.mjs tests/importDiagnostics.test.mjs tests/importMethods.test.mjs tests/chunkedXmlReader.test.mjs
```
