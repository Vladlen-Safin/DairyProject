# Инструкция системному администратору: подготовка DairyProject

Дата: 24.09.2026.

Документ содержит действующую копию конфигурации backend, включая секреты.
Передавать только ответственному администратору по защищённому каналу. Не публиковать,
не включать в Git или каталог файлов, доступных через веб-сервер. Файл исключён из Git;
после клонирования репозитория передать его на сервер отдельно.

## 1. Область работ

Подготовить PostgreSQL, конфигурацию, production-сборки backend и frontend,
постоянный запуск backend и проверить его локально. Настройка Nginx, домена,
HTTPS и публикация интерфейса выполняются позднее и в эту инструкцию не входят.
До этого этапа frontend будет собран, но ещё не доступен пользователям как сайт.

Команды ниже рассчитаны на Linux с bash и systemd. Для Windows Server требуется
другая настройка службы. Пример пути репозитория: `/opt/DairyProject`, пользователь
службы: `ediary`. Заменить путь и пользователя на фактические. Служба не должна
работать от root. Предполагается, что Node.js, npm, Git и PostgreSQL уже установлены.
Для текущего Angular 19.2 подходит Node.js 22; версии проверить командой `node --version`
и `npm --version`. Проект использует два отдельных package-lock.json.

До работ определить: путь репозитория, пользователя службы, расположение БД,
параметры подключения к FTP 1С и переносится ли существующая база.
Сервер должен иметь сетевой доступ к PostgreSQL и FTP, включая пассивные порты FTP.
Адрес локальной сети 1С на внешнем сервере может требовать VPN.

## 2. Backend: копия текущего backend/.env

Ниже точная копия локального файла на момент подготовки инструкции. Это исходные
значения для переноса, а не автоматически проверенная конфигурация сервера.
Сохранить содержимое блока в `/opt/DairyProject/backend/.env` и проверить адреса,
учётные данные и пути. Не переносить разделители Markdown в файл.

```dotenv
# ---------------------------------------------------------------------------
# PostgreSQL
# ---------------------------------------------------------------------------
DATABASE_URL=postgres://ediary:ediary@localhost:5432/ediary
DB_POOL_SIZE=10

# ---------------------------------------------------------------------------
# Локальный кэш XML-файлов, скачанных с FTP (сервер работает с ними как раньше
# с локального диска - сам механизм импорта/чекпоинтов этого не замечает)
# ---------------------------------------------------------------------------
XML_LOCAL_CACHE_DIR=./xml-cache

IMPORT_TIME_BUDGET_MS=20000

# ---------------------------------------------------------------------------
# HTTP
# ---------------------------------------------------------------------------
PORT=3000
IMPORT_API_TOKEN=

# Дополнительный секрет для bcrypt; не хранится в PostgreSQL.
PASSWORD_PEPPER=Электронный дневник

# Секрет подписи JWT (демо-авторизация фронтенда)
JWT_SECRET=dev-insecure-secret-change-me

# ---------------------------------------------------------------------------
# FTP-источник данных от 1С
# ---------------------------------------------------------------------------
FTP_HOST=192.168.8.16
FTP_PORT=21
FTP_USER=1c_dnevnik
FTP_PASSWORD=Lvbnhbqvjkjltw
FTP_SECURE=false
FTP_REMOTE_DIR=/test
```

### Назначение переменных

| Переменная | Пояснение |
|---|---|
| `DATABASE_URL` | Обязательная строка подключения к PostgreSQL. База и роль должны существовать. При смене сервера БД изменить адрес. Спецсимволы в пароле URL должны быть percent-encoded. |
| `DB_POOL_SIZE` | Максимальный размер пула соединений; по умолчанию 10. |
| `PORT` | Порт backend; по умолчанию 3000. |
| `XML_LOCAL_CACHE_DIR` | Каталог XML-кэша; по умолчанию `./xml-cache`, относительно рабочей папки backend. Пользователю службы нужны права записи. |
| `IMPORT_TIME_BUDGET_MS` | Бюджет одной итерации обработки events, по умолчанию 20000 мс. Это не предел полной длительности HTTP-запроса. |
| `IMPORT_API_TOKEN` | Секрет заголовка `x-import-token` для `/importxml`. Если пуст, проверка отключена. Перед публикацией задать секрет и согласовать его с отправителем запросов. |
| `JWT_SECRET` | Секрет подписи токенов. В production задать отдельный случайный секрет. При его смене выданные токены перестанут проходить проверку. |
| `PASSWORD_PEPPER` | Обязательный секрет для проверки паролей. При переносе существующей базы сохранить прежнее значение; произвольная замена нарушит вход пользователей. |
| `FTP_HOST` | Обязательный адрес FTP 1С, доступный с сервера приложения. |
| `FTP_PORT` | Порт FTP, по умолчанию 21. |
| `FTP_USER`, `FTP_PASSWORD` | Обязательная учётная запись FTP. |
| `FTP_SECURE` | `true` включает FTPS; по умолчанию `false`. Значение должно соответствовать серверу FTP. |
| `FTP_REMOTE_DIR` | Рабочая папка FTP; по умолчанию `/`. |
| `NODE_ENV` | Для процесса backend установить `production`; ниже это делает systemd. Само значение не исправляет ограничения безопасности кода. |

Все обязательные FTP-параметры проверяются при старте backend, даже если импорт пока
не вызывается. `.env` загружается из рабочей папки процесса. Переменные, уже заданные
в окружении процесса, имеют приоритет над значениями dotenv.

Пример прав после создания файла (выполняет администратор):

```bash
sudo chown ediary:ediary /opt/DairyProject/backend/.env
sudo chmod 600 /opt/DairyProject/backend/.env
sudo install -d -o ediary -g ediary -m 700 /opt/DairyProject/backend/xml-cache
```

Если `XML_LOCAL_CACHE_DIR` указывает на другой каталог, создать именно его.
Сохранить защищённую резервную копию секретов отдельно от резервной копии БД.

## 3. Frontend: копия текущего environment.ts

У Angular в этом проекте нет отдельного `.env`. Настройки находятся в
`dairy/src/environments/environment.ts` и встраиваются в JavaScript при сборке.
Все значения доступны пользователю браузера: секреты сюда помещать нельзя.

Текущая копия:

```typescript
export const environment = {
  production: false,
  // apiUrl: 'http://localhost:3000/api',
  apiUrl: 'http://192.168.8.125:3000/api',
};
```

| Поле | Пояснение |
|---|---|
| `production` | Поле конфигурации приложения. Оптимизацию сборки выбирает команда Angular CLI; изменение только этого поля не заменяет production-сборку. |
| `apiUrl` | Адрес API с точки зрения браузера пользователя, а не сервера. `localhost` здесь означает компьютер пользователя. |

Для будущей публикации сайта и API на одном домене перед сборкой заменить содержимое
`dairy/src/environments/environment.ts` следующим:

```typescript
export const environment = {
  production: true,
  apiUrl: '/api',
};
```

`/api` заработает для пользователей после настройки проксирования веб-сервером
на следующем этапе. Не использовать локальный IP разработчика как production-адрес.
В `angular.json` сейчас нет `fileReplacements`: команда production-сборки сама
не заменит текущий environment.ts. После любого изменения настроек пересобрать frontend.

## 4. Установить зависимости и подготовить PostgreSQL

Команды установки и сборки выполнять от пользователя развёртывания с правом записи
в репозиторий. Не копировать node_modules с компьютера разработчика.

```bash
cd /opt/DairyProject/backend
npm ci --include=dev
```

`--include=dev` нужен для TypeScript и tsx, в том числе если NODE_ENV уже установлен
в production. Скрипты миграций используют tsx. `npm ci` использует package-lock.json.

### Новая пустая база

Создать отдельную роль приложения без прав суперпользователя и базу с этой ролью
как владельцем. Например, в psql под администратором PostgreSQL:

```sql
CREATE ROLE ediary LOGIN PASSWORD 'REPLACE_WITH_STRONG_PASSWORD';
CREATE DATABASE ediary OWNER ediary;
```

Указать соответствующую строку DATABASE_URL в backend/.env. Затем из backend:

```bash
npm run migrate
npm run migrate -- 002_widen_mark_values.sql
```

### Перенос существующей базы

Сделать резервную копию исходной БД и восстановить её штатными средствами PostgreSQL.
Сохранить PASSWORD_PEPPER от этой базы. Проверить схему и применить только отсутствующие
миграции. `npm run migrate` без аргумента выполняет 001_init.sql и НЕ предназначен
для повторного запуска на существующей базе. Учёта применённых миграций пока нет.
Не удалять рабочую базу для обновления приложения.

При наличии старых паролей plain: после резервного копирования:

```bash
npm run users:hash
# Только если проверка показывает необходимость конвертации:
npm run users:hash:apply
```

Существующие bcrypt-хэши остаются без изменений. Другие старые форматы требуют
исходных паролей или повторного импорта. `npm run seed` на рабочей базе НЕ выполнять:
он очищает таблицы и создаёт тестовые данные.

## 5. Собрать и проверить backend

```bash
cd /opt/DairyProject/backend
npm run build
NODE_ENV=production npm start
```

`npm run build` создаёт `backend/dist`. `npm start` выполняет `node dist/server.js`:
это запуск собранного приложения, без tsx watch. Для production не использовать
`npm run dev`. При ошибке сборки остановить развёртывание, не запускать старый dist
как будто сборка была успешной.

Из второго терминала на сервере:

```bash
curl --fail --show-error http://127.0.0.1:3000/api/health
```

Ожидается HTTP 200 и JSON с `ok: true`, `db: true`. Счётчики могут быть нулевыми до
импорта. Если PORT изменён, подставить его во все команды проверки.
После проверки остановить ручной запуск Ctrl+C, прежде чем запускать службу.

Сейчас backend слушает не только localhost. До настройки публикации ограничить
входящий доступ к его порту средствами сети/firewall. PostgreSQL также не должен
быть доступен из интернета.

## 6. Постоянный запуск backend через systemd

Убедиться, что пользователь ediary существует, может читать код и зависимости,
читать backend/.env и писать в каталог XML-кэша. Проверить путь к Node:

```bash
command -v node
```

Создать `/etc/systemd/system/ediary-backend.service` со следующим содержимым.
В ExecStart заменить `/usr/bin/node` на фактический абсолютный путь. При использовании
nvm путь текущего пользователя может быть недоступен службе; это проверить отдельно.

```ini
[Unit]
Description=DairyProject backend
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
User=ediary
Group=ediary
WorkingDirectory=/opt/DairyProject/backend
Environment=NODE_ENV=production
ExecStart=/usr/bin/node /opt/DairyProject/backend/dist/server.js
Restart=on-failure
RestartSec=5
UMask=0077
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target
```

`.env` прочитает само приложение через dotenv благодаря WorkingDirectory.
Отдельный EnvironmentFile здесь не нужен. Если PostgreSQL расположен локально,
администратор может добавить зависимость от его фактической службы.

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ediary-backend
sudo systemctl status ediary-backend --no-pager
sudo journalctl -u ediary-backend -n 100 --no-pager
curl --fail --show-error http://127.0.0.1:3000/api/health
```

Управление:

```bash
sudo systemctl restart ediary-backend
sudo systemctl stop ediary-backend
sudo journalctl -u ediary-backend -f
```

Не запускать одновременно ручной `npm start` и службу на одном порту.
Служба продолжает работать после закрытия SSH и запускается после перезагрузки сервера.

## 7. Собрать frontend в production-режиме

После подготовки environment.ts из раздела 3:

```bash
cd /opt/DairyProject/dairy
npm ci --include=dev
npm run build -- --configuration production
```

Проверить наличие `/opt/DairyProject/dairy/dist/dairy/browser/index.html` и файлов JS/CSS.
Весь каталог `browser` — готовая сборка интерфейса для последующей раздачи веб-сервером.
Не публиковать корень репозитория: там есть служебные файлы и секреты.

**В каталоге dairy команду `npm start` на production не выполнять:** она запускает
`ng serve`. Для frontend не нужен постоянно работающий процесс Node.js после сборки.
На этом этапе сборка готова; доступ пользователей, HTTPS и маршрутизация Angular
будут настроены отдельно вместе с Nginx.

## 8. Проверка FTP и первичный импорт

Из backend, с теми же настройками, что у службы:

```bash
cd /opt/DairyProject/backend
npm run ftp:check
```

Импорт пишет в БД и отправляет result.xml обратно в 1С. Первую загрузку согласовать
с ответственным за 1С и запускать после подготовки/резервного копирования базы.
Вызвать POST /importxml с заголовком x-import-token, равным IMPORT_API_TOKEN из .env.
Не записывать секрет в историю команд. Пример bash с вводом без отображения:

```bash
read -r -s -p 'IMPORT_API_TOKEN: ' IMPORT_TOKEN_INPUT
printf '\n'
while true; do
  result=$(printf 'x-import-token: %s\n' "$IMPORT_TOKEN_INPUT" | curl --fail-with-body --silent --show-error -X POST -H @- http://127.0.0.1:3000/importxml) || break
  printf '%s\n' "$result"
  [ "$result" = CONTINUE ] || break
done
unset IMPORT_TOKEN_INPUT
```

DONE — обработка завершена; ALREADY — сообщение уже зарегистрировано как обработанное;
CONTINUE — нужна следующая итерация; ERROR/NONE — проверить журнал и результаты импорта;
UNAUTHORIZED — проверить токен. ALREADY само по себе не подтверждает отсутствие ошибок
предыдущего импорта. Не удалять XML-кэш между итерациями CONTINUE.
Встроенного расписания нет: автоматический обмен настраивается отдельно с 1С.

## 9. Обновление и критерии готовности

Перед обновлением сохранить резервную копию БД и предыдущий релиз. Подготовить новую
версию и обе сборки, проверить результат, применить только необходимые миграции,
перезапустить backend через systemd и проверить health. Для сборки в рабочем каталоге
предусмотреть окно обслуживания; предпочтительно готовить релиз в отдельной папке.
Откат кода не отменяет миграции БД. .env и XML-кэш не заменять файлами нового релиза.

Результат текущего этапа:

- Backend собран и работает как служба с NODE_ENV=production.
- Health подтверждает подключение к базе, после перезапуска службы проверка проходит.
- FTP доступен, результат согласованного импорта проверен.
- Frontend собран с согласованным apiUrl; каталог browser готов для веб-сервера.
- Секреты доступны только ответственным пользователям; настроены копии БД и секретов,
  проверено восстановление, ограничен размер журналов.
- Конфигурация Nginx и публичный доступ остаются отдельным этапом.

Перед публичным запуском разработчику необходимо закрыть общие API с оценками,
исправить проверку типов JWT, настроить безопасные cookie/CORS и защиту входа.
Текущие ограничения перечислены в backend/README.md. Production-сборка не устраняет их.
